**KBL 공개 데이터를 이용한 RAG 전환 전략**

검토일: 2026-10-25. 이 문서는 공개 데이터의 구조와 현재 코드의 연결 지점을 확인한 도입 제안이다. 전체 코퍼스의 품질 검증, 검색 성능 실험, 데이터 교체는 아직 수행하지 않았다.

후속 구현: 제공 후보 52문항 및 전체 법령 220,160개/281,402청크의 BM25를 준비하고, 기존 Qdrant와 설정으로 전환하도록 연결했다. 아래 제안 당시의 분석은 보존한다. 실제 사용법·현재 지원 범위는 [KBL 사용 안내](KBL_USAGE.md)를 따른다.

권고는 **제공된 검색 후보를 재생하는 실험부터 시작하고, 새 질문을 받아야 하는 시점에 공개 코퍼스의 BM25 검색을 추가하는 것**이다. 공개 데이터를 쓰는 것과 벡터 DB를 쓰지 않는 것은 별개의 선택이다. 아래 두 단계는 모두 기존 사설 벡터 DB 없이 진행할 수 있다.

**1. 링크의 데이터는 어떤 용도인가**

사용자가 지정한 대상은 `lbox/kbl`의 `fc30b6d78a75adf396e606afa3b188bda3d711b0` 커밋이다. `knowledge`의 기본 파일은 법률 지식 평가 문제이며, 질문·선택지·정답을 담는다. 검색 원문 코퍼스와 구분해서 사용해야 한다. [지정한 knowledge 폴더](https://huggingface.co/datasets/lbox/kbl/tree/fc30b6d78a75adf396e606afa3b188bda3d711b0/knowledge)

이번 검토에서 기본 JSON 7개를 모두 읽어 다음 건수를 확인했다. 합계는 510문항이다. 숫자는 폴더 표시 크기로 추정한 값이 아니라 실제 JSON 배열의 길이다.

| 유형 | 파일명의 핵심 부분 | 문항 수 | 도입 시 역할 |
|---|---|---:|---|
| 법률 개념 | `legal_concept_qa` | 100 | 용어·개념 식별 평가 |
| 범죄 구성요건 | `offense_component_qa` | 102 | 사실관계와 법적 요건의 연결 평가 |
| 질문과 법조문 연결 | `query_and_statute_matching_qa` | 52 | 최초 연결 검증 대상으로 권고 |
| 법령 환각 | `statute_hallucination_qa` | 75 | 존재하지 않는 법령 등 혼동 평가 |
| 법률 상식 오해 | `legal_common_legal_mistake_qa` | 41 | 일반적 오해 평가 |
| 법률 상식 오해·이유 | `legal_common_legal_mistake_qa_reasoning` | 40 | 이유가 포함된 선택지 평가 |
| 조문 번호와 내용 연결 | `statute_matching_qa_number_and_content_matching_qa` | 100 | 별도 평가 트랙 |

공통 필드는 `doc-id`, `question`, `label`과 `A`~`E` 중 해당하는 선택지다. 선택지 수는 유형별로 다르다. 질문과 법조문 연결 유형에는 `label_long`도 있다. `label`과 `label_long`은 정답 영역으로 분리한다. 전체 JSON을 문자열로 바꿔 검색 문서나 모델 입력으로 넣으면 정답 누출이 발생한다. [실제 STATq 파일](https://huggingface.co/datasets/lbox/kbl/blob/fc30b6d78a75adf396e606afa3b188bda3d711b0/knowledge/kbl_query_and_statute_matching_qa_v0.1.json)

같은 폴더의 `rag_s`, `rag_p`, `rag_ps`는 이미 검색한 문서를 질문과 함께 제공한다. 확인한 샘플에서 각각 법령, 판례, 두 종류의 혼합 후보였다. 지정 커밋에는 각 변형별 6개 유형의 RAG 파일이 있고, 위 표의 마지막 100문항 유형에 대응하는 RAG 파일은 없다. 따라서 **510문항 전체에 사전 검색 후보가 제공된다고 가정하지 않는다**.

확인한 구조는 다음과 같다. 아래는 필드 구조만 나타낸 것이며 값 예시는 생략했다.

```text
질문 레코드
  doc-id, question, A, B, ...
  label, label_long                   → 평가 전용 저장소
  rag_data
    question_only
      query
      retrieved_docs
        results[]
          doc_id, score, title, passage → 검색 후보
    question_and_individual_answers   → 유형별 존재·내용 확인 필요
```

STATq의 `rag_s` 파일은 전체 52문항을 확인했고 모든 문항에 후보 10개가 있었다. `rag_p`·`rag_ps`는 파일 앞부분에서 첫 문항을 확인했으며 각각 후보 10개·20개였다. 이 두 숫자는 전체 파일에 대한 보장이 아니다. 혼합 후보의 `title`이 `null`인 샘플도 있었다. 원문 길이는 첫 판례 후보 집합에서 최대 30,863자로, 법령보다 훨씬 긴 문서가 포함됐다. [확인한 rag_s 파일](https://huggingface.co/datasets/lbox/kbl/blob/fc30b6d78a75adf396e606afa3b188bda3d711b0/knowledge/rag_s/kbl_query_and_statute_matching_qa_v0.1.rag.json)

**2. 실제 검색 코퍼스와 이용 조건**

새 질문을 검색하려면 별도 데이터셋인 `lbox/kbl-rag`의 `corpus`를 사용한다. 공식 저장소도 법령 코퍼스 로딩 경로를 `lbox/kbl-rag`로 안내한다. 검토 당시 이 저장소의 HEAD는 `72f50c8d2b44defa56ceff3fef62128b94f78bba`였다. [공식 KBL 저장소](https://github.com/lbox-kr/kbl), [공개 RAG 저장소](https://huggingface.co/datasets/lbox/kbl-rag/tree/main)

| 원문 파일 | API에 표시된 바이트 수 | 약식 크기·용도 |
|---|---:|---|
| `corpus/statutes.jsonl` | 206,953,775 | 약 207 MB, 법령부터 시작할 때 |
| `corpus/precedents.jsonl` | 1,162,200,003 | 약 1.16 GB, 판례 확장 |
| `corpus/precedents_and_statutes.jsonl` | 1,376,646,498 | 약 1.38 GB, 혼합 코퍼스 |

크기는 다운로드 파일 기준의 십진 단위다. 인덱스·캐시·메모리 요구량과 다르다. 세 파일을 모두 내려받아 합치지 않는다. 혼합 파일을 쓰거나 개별 두 파일을 쓰는 방식을 선택하고 중복·ID 대응을 검증한다. [파일 메타데이터 API](https://huggingface.co/api/datasets/lbox/kbl-rag/tree/72f50c8d2b44defa56ceff3fef62128b94f78bba/corpus)

부분 샘플에서 코퍼스 레코드는 `id`, `contents` 두 필드였다. 전체 코퍼스의 필드 분포·건수·중복률은 아직 검사하지 않았다. 공개 자료가 바로 현재 `Document` 스키마에 들어가는 형태는 아니므로 변환기가 필요하다.

라이선스는 KBL과 KBL-RAG 모두 **CC BY-NC 4.0**으로 표시되어 있다. 출처·라이선스·변경 사항을 기록하고 비영리 조건을 지켜야 한다. 상용 제품이나 매출과 연결된 활용에 자유롭게 쓸 수 있는 데이터로 간주하지 않는다. 기업 내부 실험도 사용 목적에 따른 검토가 필요하다. 상업적 이용이 필요하면 권리자에게 해당 이용 범위를 확인하거나 별도 허가를 확보하는 경로를 잡는다. [KBL 라이선스 표시](https://huggingface.co/datasets/lbox/kbl/blob/fc30b6d78a75adf396e606afa3b188bda3d711b0/README.md), [KBL-RAG 라이선스 표시](https://huggingface.co/datasets/lbox/kbl-rag), [CC BY-NC 4.0 조건](https://creativecommons.org/licenses/by-nc/4.0/)

최신 법률 서비스의 원문으로 사용하기에는 추가 작업이 크다. 공식 README는 법령을 2024년 11월 덤프로 소개하지만, 논문은 2023년 11월 기준이라고 설명하고 실제 샘플 ID에도 `dumpdate-20231128`이 들어 있다. 이 차이가 모든 레코드에서 어떻게 나타나는지는 미확인이다. 다운로드 날짜나 저장소 커밋 날짜를 법령의 시행일로 사용하지 않는다. 현재 시점의 유효성을 주장하려면 공식 법령 원문·개정 이력과 대조해야 한다. [공식 README](https://github.com/lbox-kr/kbl#corpus), [논문 §3.4](https://aclanthology.org/2024.findings-emnlp.319.pdf)

**3. 도입 경로의 선택**

| 경로 | 기존 벡터 DB | 새 질문 검색 | 필요한 신규 작업 | 적합한 목적 |
|---|---|---|---|---|
| A. 공개 검색 후보 재생 | 사용 안 함 | 지원 안 함 | JSON 변환·후보 재생·객관식 평가 | CE·Jev 비교를 빠르게 검증 |
| B. 공개 코퍼스 + BM25 | 사용 안 함 | 지원 | 원문 변환·어휘 인덱스·검색 연결 | 벡터 DB 없이 RAG 운영 실험 |
| C. 공개 코퍼스 + 새 벡터 인덱스 | 기존 것은 사용 안 함 | 지원 | 원문 변환·전체 재임베딩·새 컬렉션 | 기존 dense 검색 구조 유지 |

우선순위는 A → B다. 사용자 의도가 기존 사설 데이터만 교체하는 것이라면 C도 가능하다. 벡터 DB 자체를 없애고 싶다면 B를 선택한다. 어느 경로도 Hugging Face를 바로 연결 가능한 검색 API로 취급하지 않는다. 공개된 것은 데이터 파일이며, B에는 어휘 검색 인덱스가, C에는 새 벡터 인덱스가 필요하다.

공개 논문은 BM25 검색을 사용했다. 따라서 B는 공개 데이터의 원래 평가 맥락과도 맞는다. 다만 우리 토크나이저·검색 설정이 달라지면 논문 검색의 정확한 재현이라고 부르지 않는다. [논문 §4.2](https://aclanthology.org/2024.findings-emnlp.319.pdf)

**4. A 경로: DB 없이 제공 후보로 실험하기**

첫 대상은 STATq 52문항과 대응하는 `rag_s` 파일로 잡는다. 법령 후보가 비교적 짧고, 질문→후보→재채점→선택→답변의 연결을 확인하기 쉽다. 소규모 연결 검증이며, Jev 우월성이나 2%p 비열등성을 입증하는 표본으로 사용하지 않는다.

처리 순서는 다음과 같다.

1. 지정 커밋의 기본 문제 파일과 RAG 파일을 내려받아 파일별 SHA-256·라이선스·출처를 기록한다.
2. `유형 + doc-id`로 문제 ID를 만든다. 파일마다 `doc-id`가 다시 시작하므로 숫자만 전역 ID로 쓰지 않는다.
3. 평가 정답을 별도 파일로 분리한다. 생성·CE·Jev에 허용할 필드는 질문, 선택지, 검색 원문과 출처뿐이다.
4. 후보의 `passage`를 본문으로, 원래 `doc_id`를 출처 ID로 보존한다. 원문 해시·정규화 버전으로 내부 ID를 고정하고 동일 출처의 판본 충돌을 기록한다.
5. `question_only`의 검색 결과 순서·점수를 그대로 재생한다. 모든 비교 방법에 같은 후보 목록을 준다. 확인한 STATq에서는 K=10이며, 현재 기본값 K=20에 맞추려고 문서를 복제하거나 다른 질문의 후보를 보충하지 않는다.
6. 최초에는 제공 순서 상위 N개, CE-R, Jev-R을 비교한다. N=5를 초기값으로 삼되 문맥 예산과 함께 고정한다. FR은 개발 데이터에서 문턱값을 선정한 뒤 추가한다.
7. 객관식 정답률·응답 형식 오류·보류율·토큰·재채점/생성 비용을 기록한다. 전체 검색 비용·검색 지연은 제공 자료만으로 알 수 없으므로 별도 미측정으로 남긴다.

이 경로의 주장은 **동일한 공개 검색 후보 안에서 재채점과 선택 방식이 답변에 미치는 영향**이다. 검색 성능 전체나 새 질문 대응 성능을 검증하는 경로는 아니다. 후보 재생의 로컬 파일 읽기 비용은 측정할 수 있지만 원래 검색 비용을 대체하지 않는다.

`rag_s`에서 검증한 뒤 `rag_p`, `rag_ps`와 다른 유형으로 넓힌다. 후보 수·쿼리 분기·제목 누락·중복을 파일별로 다시 검사한다. 특히 법령 환각 유형은 논문에서 선택지별 검색을 사용하므로 `question_only`만 일괄 선택하지 않는다. 선택지별 후보를 합치는 실험을 한다면 중복 제거·순서·K 정책을 고정하고 원래 평가와 다른 설정임을 기록한다. [논문 §4.2](https://aclanthology.org/2024.findings-emnlp.319.pdf)

제공 후보를 전부 모아 작은 검색 코퍼스로 만드는 방식은 초기 운영 경로로 권하지 않는다. 평가 질문에 맞춰 검색된 부분집합이므로, 전체 법률 코퍼스의 커버리지나 일반 검색 성능을 대표하지 못한다.

**5. B 경로: 공개 코퍼스로 새 질문 검색하기**

먼저 `statutes.jsonl`만 도입하고, 판례는 다음 단계에서 추가한다. 전체 다운로드 뒤 건수·빈 본문·중복 ID·동일 ID의 본문 차이·문서 길이·법령명 추출률을 검사한다. 파일 크기와 논문 수치를 실제 검증 결과로 대신하지 않는다.

현재 `Document`로의 기본 대응은 다음과 같다.

| 현재 필드 | 공개 코퍼스에서의 대응 |
|---|---|
| `text` | `contents`를 현재 NFC 정규화 함수에 통과시킨 본문 |
| `doc_id` | `kbl:statute:` 또는 `kbl:precedent:` 접두어 + 원본 `id` |
| `version_id` | 데이터셋 커밋·본문 해시로 식별한 수집 판본. 법적 시행 판본과 구분 |
| `group_id` | 법령 가족·사건 가족 식별자. 복원이 안 되면 독립 분할 근거가 약함을 기록 |
| `doc_type` | 원본 파일에 따라 statute / precedent |
| `jurisdiction` | 이 코퍼스의 대한민국 법률 범위라는 출처 근거 아래 KR |
| `title`, `citation_key` | 원문에서 확인되는 법령명·조문·사건번호만 추출. 미확인은 출처 ID로 표시 |
| `source_uri` | 고정 커밋의 실제 파일 URL. 레코드 ID는 별도 원본 매핑에 보존 |
| `source_hash` | 변환 전 레코드의 안정적 직렬화 해시 |
| `collected_at` | 우리 수집일 |
| `effective_from`, `effective_to` | 원문 근거가 없으면 null |

법령 조문은 우선 원래 레코드를 유지해 BM25를 구성한다. 판례는 주문·이유 등 구조 경계를 이용해 분할하고 원문 위치를 보존한다. 긴 판례를 CE의 512 토큰 한도로 앞부분만 잘라 점수화하면, 생성기에 전달하는 근거와 재채점 대상이 달라질 수 있다. 공통 청크 정책 또는 CE의 윈도 평가 정책을 먼저 정하고 원문 전체를 보는 조건과 결과를 섞지 않는다.

검색 흐름은 질문 → BM25 공통 후보 K개 → CE/Jev → 선택 N개 또는 FR → 생성 → 인용 검증으로 잡는다. 형태소 처리·문자 정규화·조문 번호의 토큰 처리를 고정하고 개발 질문으로 점검한다. 판례 추가 시에는 각 코퍼스를 따로 검색하고 BM25 점수만 단순 비교하기보다 단일 혼합 인덱스 또는 개발 데이터로 고정한 순위 결합을 사용한다.

우리 `lexical.py`는 이미 BM25 형태의 보조 검색을 구현하지만 **정답 근거 탐색을 위한 보조 도구**이며 전체 문서를 질문마다 순회한다. 이를 그대로 전체 코퍼스의 서비스 검색으로 바꾸지 않는다. 작은 파일럿에서 분석기를 검증하는 참고 구현으로 쓰고, 전체 코퍼스에서는 역색인·저장·재로딩·메모리 요구량을 갖춘 검색 백엔드를 연결한다.

정확한 원 논문 재현이 목표면 공식 Pyserini/Lucene 경로와 분석기·버전을 확인해 고정한다. 운영 단순화가 우선이면 다른 BM25 구현도 선택할 수 있지만, 공개 코퍼스를 이용한 별도 검색 설정으로 보고한다.

효력 시점은 두 모드로 나눈다. 역사 스냅샷 실험에서는 기준일을 자동으로 오늘로 채우지 않고, 시점 검증을 하지 않는다는 범위를 실행 기록에 남긴다. 현재 법률 질문에 답하는 모드는 공식 개정 이력·시행일 매핑을 갖춘 뒤 제공한다. 현재 코드의 `unknown_temporal_policy: exclude`에서 시행일 미상 자료에 오늘 날짜를 넣으면 후보가 모두 빠질 수 있다. 이를 해결하려고 임의의 시행일을 채우지 않는다.

**6. 현재 저장소에서 바꿔야 할 지점**

단순히 YAML의 문서 경로나 `QDRANT_COLLECTION`을 바꾸는 것으로 A·B 경로가 동작하지 않는다. 현재 `run`, `freeze`, `protocol`, 뷰어의 질문 처리까지 벡터 인덱스에 연결되어 있다.

| 위치 | 현재 상태 | 필요한 변경 |
|---|---|---|
| `schema.py` | `Query`는 answerable=true일 때 충분 근거 집합을 요구 | 별도 객관식 `BenchmarkQuery` 및 정답 저장 형식 추가. 기존 연구용 gold 검증 유지 |
| 신규 `kbl_import.py` | KBL 변환기 없음 | 문제·정답·후보·출처를 분리하고 충돌·누락 검사 |
| `config.py` | 검색 경로가 Qdrant 중심 | 제안 필드 `retriever_backend: vector / replay / bm25`와 자료 경로 추가. 현재 미지원 |
| 신규 검색 팩터리·어댑터 | 공통 검색 인터페이스 없음 | replay/BM25가 `manifest`, 후보 목록, trace를 반환하도록 구현 |
| `pipeline.py` | `run`·`freeze`가 `VectorIndex` 직접 생성, protocol이 벡터 manifest 읽음 | 검색 팩터리와 백엔드별 manifest 사용. replay/BM25에서 embedding identity 요구 제거 |
| `pipeline.py` 비용·시간 | 검색 trace에 embedding 항목을 전제 | 재생·실측 검색·추정 비용을 구분. 미측정 총비용은 null 유지 |
| `cli.py` | 수집·smoke·benchmark 등에서도 벡터 경로 사용 | 관련 진입점 전체에 동일 검색 선택 적용. import/MCQ 평가 명령 추가 |
| `prompts.py`, 생성 후처리 | 자유서술형 JSON 답변 | MCQ 전용 입력·정답 문자 파싱 추가. 선택지를 모든 조건에 동일하게 제공 |
| `evaluation.py` | 충분 근거 집합·사람 판정 중심 | 독립 MCQ 정확도 집계. 기존 `accuracy`·ESR 의미를 덮어쓰지 않음 |
| `viewer.py` | 임의 질문을 받는 managed/existing 인덱스 | BM25 질의 연결. replay는 준비된 문항만 실행하고 새 질문 실행 차단 |
| `viewer_static/app.js` | 기준 방법을 Vector라고 표시 | 실제 BM25/제공 검색 순서 이름 표시. 원 순위·점수도 벡터 점수로 오인하지 않도록 분리 |

검색만 사용하는 기준 방법은 새 `retrieval` 방법으로 일반화하고 UI에는 `BM25` 또는 `제공 순서`로 표시하는 설계를 권고한다. `METHODS`, `default_conditions`, `query_rows`의 재채점 대상 분기, `select`의 점수·동점 처리도 같이 수정한다. 기존 Vector 결과는 그대로 읽을 수 있게 하되 BM25 실험 결과에 Vector 이름을 쓰지 않는다.

현재 `Query`의 검증을 우회하려고 빈 충분 근거 집합에 answerable=true를 넣거나, 정답 보기 하나를 근거 집합으로 만들어 넣지 않는다. 객관식 문제와 근거 충분성 평가 질문은 다른 스키마로 유지한다. MCQ 생성 결과는 기존 `Answer`를 활용하되 `answer`에는 정답 문자 하나를 넣고, 별도 평가기가 허용된 보기 문자인지 검사하는 방식으로 시작할 수 있다. `rationale`·`claims`·`citations`는 정답 문자 일치와 별도로 평가한다.

**7. 평가 설계와 누출 방지**

평가 데이터가 공개되어 있어 모델의 사전학습 노출 가능성을 배제할 수 없다. 동일 생성기로 검색 근거 없음/제공 순서/CE-R/Jev-R을 비교하고, 이 결과를 새로운 비공개 법률 질문에 대한 일반화 성능으로 확대하지 않는다. 검색 근거 없음은 모델 지식 평가이며 현재의 “제공 근거만 사용하고 부족하면 보류” 프롬프트와 다른 평가 조건이므로 별도 기록한다.

| 측정 대상 | 초기 KBL 실험에서 가능한 범위 |
|---|---|
| 객관식 정확도 | `label`과 엄격하게 파싱한 출력 문자 비교. 유형별·문항 가중 평균·유형 평균 구분 |
| 응답 형식 오류 | 허용하지 않은 문자·여러 답·파싱 실패를 기록하고 전체 분모에서 오답 처리 |
| 보류 | 정답 문자와 별도로 보류·미응답률을 보고. HALL의 정답이 “없음”인 보기와 생성 보류를 구분 |
| ESR@N, 근거 Recall | 충분 근거 집합을 별도 주석하기 전에는 미측정 |
| nDCG | 후보 관련성 등급을 주석하기 전에는 미측정 |
| 근거 있는 정답 | 객관식 일치만으로 인정하지 않음. 핵심 주장·인용·근거 충분성 검토 필요 |
| 비용·시간 | A는 재채점/생성과 재생 처리 실측만. B/C는 검색을 포함해 별도 측정 |

정답 문자나 `label_long`이 있다는 사실은 근거 문서 gold가 있다는 뜻이 아니다. 참조 조문과 원문이 대응하면 근거 주석의 초안으로 활용하되, 조문 단위 매칭과 충분한 근거 집합 확정은 구분한다. 객관식 문항에 정답이 있어도 제공된 후보만으로는 답할 수 없을 수 있다.

우리 기존 연구 질문인 Jev-R 대 CE-R의 ESR·근거 있는 정답 비교를 유지하려면, 후보·원문에서 gold 근거를 다시 확인하고 필요한 충분 근거 집합과 사람 판정을 추가해야 한다. 미회수된 gold는 존재하지 않는 근거로 처리하지 않고 후보 회수 실패로 남긴다.

개발/시험은 단순 문항 무작위 분할을 피한다. 이유 포함/미포함의 유사 질문, 같은 법률 쟁점, 동일 법령·사건 가족을 연결해 분리하고, gold 정답을 본 파일럿 문항은 최종 미노출 시험에 재사용하지 않는다. 공유된 모든 검색 잡음 문서까지 하나의 그룹으로 묶으면 거대 연결 집합이 생길 수 있으므로 그룹은 실제 출제 원문·gold·쟁점 관계를 근거로 만들고 독립 그룹 수를 보고한다. KBL 전체를 외부 시험으로 남기려면 FR 문턱값은 독립 개발 자료에서 정한다.

52문항은 연결 검증에 적합하다. 510문항 전체도 독립적인 법률 문제 수·task 구성·효과 크기를 확인하지 않고 기존의 pilot/dev/test 목표 표본을 충족했다고 간주하지 않는다. FR 문턱값, 토큰 예산, 검색 분석기, K/N은 시험 전에 잠그고 표본 수 산정은 독립 그룹 기준으로 다시 한다.

**8. 실행 순서와 완료 기준**

다음 순서는 구현 우선순위이며 실제 일정·API 예산은 파일럿의 토큰과 응답 시간을 측정한 뒤 산정한다.

| 순서 | 작업·산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1 | 사용 목적·라이선스 기록, 고정 커밋 source manifest | 이용 범위·출처·파일 해시 확인 |
| 2 | STATq 52문항 import 및 replay 어댑터 | 문제/정답 분리, 문항별 후보 10개·ID·본문 일치 확인 |
| 3 | 소수 파일럿에서 제공 순서/CE-R/Jev-R 실행 | 정답 비전송, 동일 후보·문맥 정책, 오류·usage 기록 확인 |
| 4 | 6개 RAG 유형으로 확장, 다른 100문항은 별도 트랙 | 유형별 분기·후보 수·길이 검사 및 시험 분할 확정 |
| 5 | 법령 전체 변환·BM25 인덱스 | 전체 ID/해시 검사, 새 질문 검색, 재실행 결과 재현 |
| 6 | 판례 추가·근거 주석·FR 개발 | 장문 처리, 주석 일치도, 독립 개발/시험, 품질·비용 기준 잠금 |
| 7 | 필요 시 현재 법령 보강 | 실제 시행일·개정 이력 매핑과 현행성 검증 |

예산은 `문항 수 × 문항별 후보 수 × 재채점 요청 정책 × 문서 길이`와 생성기의 입력/출력 토큰으로 계산한다. CE·Jev 점수는 같은 질문·후보·모델에 대해 재사용하고 R/FR은 선택 단계에서 나눠 중복 호출을 줄인다. 품질 실험 캐시와 실제 온라인 지연·비용 측정은 분리한다. 기존 provider 단가·usage 수집이 없으면 비용은 확정하지 않는다.

연결 검증에는 gold 누출 차단, 원본 후보 순서·해시 보존, 없는 문항의 replay 차단, ID 충돌, FR 문턱값 미지정, 정답 파싱 실패, metadata 미상, 긴 판례 절단 후 인용 범위, protocol freeze 이후 변경 감지를 포함한다. 실제 호출 전에 작은 고정 fixture로 확인하고, 이후 유료 호출은 파일럿 범위에서 측정한다.

추천 산출물 경로는 `data/kbl/<benchmark_revision>/` 아래의 source manifest·benchmark questions·평가 전용 gold·후보·원문 매핑, `indexes/kbl-bm25/`의 검색 manifest, `configs/kbl-replay.yaml`·`configs/kbl-bm25.yaml`, `results/kbl/`다. 이 경로와 설정 파일은 제안이며 아직 생성하거나 지원한 것이 아니다.

이 검토로 생성한 실제 산출물은 이 전략과 `research/kbl_source_audit.json`이다. 감사 JSON에는 다운로드 범위·샘플 스키마·실제 문항 수·파일 크기·해시를 남겼다. 부분 파일의 해시는 다운로드한 앞부분의 해시이며 전체 원본 파일의 SHA-256으로 사용하면 안 된다. 전체 코퍼스 다운로드·새 인덱스 구축·유료 모델 호출·기존 DB 변경은 이 검토에 포함하지 않았다.
