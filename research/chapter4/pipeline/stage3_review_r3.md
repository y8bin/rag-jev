### 요약 (Summary Assessment)

제4장은 KoBLEX 226문항으로 ParSeR의 재정렬기를 Cross-Encoder(CE)에서 Jev로 바꾼 효과를 세 축으로 보고한다. 근거 선택 품질, 재정렬 품질과 지연, 자동 답변 품질과 자원 사용이다. 배포 관점에서 보면 이 장은 드물게 정직하다. 지연을 캐시 없이 반복 측정했고, 배포 조건 의존성과 E2E가 아니라는 점을 밝혔으며, Jev의 top-10 재현율(2/180)도 공개했다. 그런데 "CE를 Jev로 바꿀 것인가"를 판단하려는 실무 독자에게는 정보가 가장 필요한 지점에서 비어 있다. 가장 중요한 공백은 세 가지다.

1. 재정렬 단계의 +5.64초가 전체 응답시간에서 얼마만큼인지 가늠할 단서가 없다. 그런데 저장된 API trace로 대략적인 규모는 산출할 수 있다.
2. "자원 사용"을 생성 단계 토큰만으로 보고한다. 기록을 보면 토큰을 가장 많이 쓰는 단계는 LLM 선택 호출로 보인다.
3. Jev 비결정성의 운영 함의(감사·회귀 테스트, 재호출 분산의 꼬리)가 평균 겹침 91.51% 한 수치로만 요약되고, RQ1 결과와 떨어진 4.3절 끝에 놓여 있다.

어느 것도 핵심 결론을 뒤집지는 않는다. 그리고 모두 기존 자료로 보완할 수 있다. 장의 유보 서술은 이미 촘촘하므로, 유보 문장을 더 늘리기보다 **정규화된 운영 수치**(호출당·쌍당 지연, 문항당 비용, 단계별 비중)를 몇 개 더하는 쪽이 효과가 크다.

### S3: 외부 API 재정렬기의 재현성을 직접 측정해 공개했다

사용량(요구량)과 청구액, 그리고 Token F1의 공백 단위와 tokenizer 토큰을 구분했다. 비용 회계를 둘러싼 오독을 미리 막는다. 입력량 절감이 관찰되지 않았다는 음의 결과를 그대로 보고한 점도 신뢰를 높인다.

### S5: 공개 코드 결함 수정 효과를 모델 교체 효과와 분리했다
**Evidence Anchor**: text: §4.2 l.21 "수정 CE와의 9.85점 차이는 후보 목록 참조 수정 효과이며, Jev 교체 효과와 구별된다"

운영 관점에서는 "모델을 바꾸는 것"보다 "파이프라인 버그를 고치는 것"이 효과가 세 배 크다는 사실이 그 자체로 실무 교훈이다. 두 효과를 섞지 않았기 때문에 이 교훈이 오염되지 않았다.

### W1: 재정렬 지연 차이(+5.64초)를 전체 응답시간 안에서 가늠할 단서가 없다 (P1)
- **Severity**: Major
- **Evidence Anchor**: text: §4.3 l.44 "예상 법령 생성·BM25·LLM 선택·답변 생성·모델 로드를 제외하므로 전체 응답시간의 차이를 뜻하지 않는다"
- **Confidence**: 4 — 프로덕션 RAG의 latency budget 설계 경험. 아래 수치는 심사자가 trace를 거칠게 분류해 얻은 것이므로 저자 확인이 필요하다.

**문제.** 이 장은 RQ2를 품질–지연 trade-off로 제시한다. 그런데 배포 결정에서 중요한 것은 "재정렬이 2.25배 느리다"가 아니라 "전체 응답이 얼마나 느려지는가"다. 장은 이 차이가 E2E 차이가 아니라고 바르게 밝혔지만, 독자가 규모를 짐작할 단서는 하나도 주지 않는다. 그 결과 trade-off의 실무적 무게를 판단할 수 없다.

**기존 자료로 가능한 보완.** 새 실험 없이 할 수 있다. `results/koblex-reproduction-v1/responses/`의 1,659개 trace에 호출별 `latency_ms`, 사용량, 비용이 저장되어 있다. 심사자가 입력 토큰 구간으로 호출 유형을 거칠게 분류해 보니 다음과 같았다(분류는 심사자의 추정이다).

| 추정 호출 유형 | 입력 토큰 | 호출 수 | 중앙 지연 | 비고 |
| --- | --- | --- | --- | --- |
| 예상 법령 생성 | 1.5–2k | 226 | 약 1.4초 | 출력 중앙값 약 100토큰 |
| 답변 생성 | 2–3k | 480 | 약 1.1초 | |
| 목록별 LLM 선택 | 3k 초과 | 953 | 약 0.8초/호출 | 출력 약 1토큰 |

문항당 목록이 약 2.1개라는 점을 감안해 순차 경로를 어림하면 LLM 단계 합은 대략 3–4초다. 이에 비해 재정렬은 CE 5.0초, Jev 10.6초다. 이 어림이 맞다면 **재정렬이 임계 경로에서 가장 큰 단일 단계일 수 있고**, Jev 교체는 전체 응답시간을 대략 1.5–2배로 늘릴 수 있다. 이 해석은 "재정렬만 2.25배"보다 실무적 함의가 훨씬 강하다. 반대로 어림이 틀렸다면 그것도 독자가 알아야 할 정보다.

**제안.**
- (a) 4.3절 지연 문단 끝에 1–2문장을 추가한다. 품질 실행 trace에서 LLM 단계의 호출당 지연 중앙값을 보고하고, "다른 세션·캐시·속도 제한 대기 조건이므로 E2E 측정이 아닌 규모 참고치"라고 명시한다. 보충자료 S3의 "실행 시간은 공정 비교에 쓸 수 없다"는 문장은 실행 전체 wall-clock에 해당한다. 호출 단위 `latency_ms`도 같은 문제가 있는지 저자가 확인하고, 적용 범위를 구분해 서술할 것을 권한다.
- (b) 위 내용을 쓰기 어렵다면, 적어도 파이프라인의 순차 호출 구조(문항당 LLM 호출 수와 직렬·병렬 여부)를 한 문장으로 적어 독자가 규모를 추정할 수 있게 한다.
- (c) E2E 동시 측정은 선택적 후속 연구로 둔다(아래 "선택적 후속 연구" 1번).

### W2: "자원 사용 특성"이 생성 단계만 다루고, 가장 큰 소비 단계로 보이는 LLM 선택 호출을 빠뜨렸다 (P1)
- **Severity**: Major
- **Evidence Anchor**: text: §4.4 l.52 "선택 문맥은 평균 203.67토큰에서 215.60토큰으로, 전체 API 입력은 2302.67토큰에서 2314.58토큰으로 늘었다"
- **Confidence**: 4 — LLM 파이프라인 토큰·비용 회계 경험. 호출 유형 분류는 심사자의 추정이다.

**문제.** 4.4절 제목과 RQ3는 "자원 사용 특성"을 내세운다. 그런데 보고된 사용량은 답변 생성 호출 하나뿐이다. trace를 보면 목록별 LLM 선택 호출은 호출당 입력이 3k 토큰을 넘고(후보 10개 포함), 문항당 약 2.1회 발생한다. 따라서 문항당 토큰과 비용의 대부분은 선택 단계에서 나올 가능성이 크다. 심사자 어림으로 선택 호출 평균 비용은 약 $0.0116/호출이고, 답변 생성은 약 $0.005/호출이다.

**두 가지 함의가 빠져 있다.**
1. 재정렬기 교체는 shortlist 내용을 바꾸므로 선택 호출의 입력량도 바꾼다. 조건 간 차이가 클 가능성은 낮지만, 보고하지 않으면 "입력량 절감 미관찰"이라는 결론의 적용 범위가 생성 단계에 국한된다는 점이 드러나지 않는다.
2. 본문 수치만으로도 선택 문맥은 전체 생성 입력의 약 9%다(215.60/2314.58). 근거 수를 줄이는 어떤 개입(4.4절의 필터링 포함)도 생성 입력을 최대 약 9%까지만 줄일 수 있다는 구조적 상한이 있다는 뜻이다. 실무 독자에게 이것은 "근거 개수 최적화로는 비용을 크게 줄일 수 없다"는 핵심 메시지인데, 본문은 이를 말하지 않는다.

**제안.**
- (a) 저장된 trace에서 선택 단계의 조건별 평균 입력·출력 토큰을 산출해 S6 표에 한 행으로 넣는다(유료 호출 없음). 본문에는 "생성 단계 기준"이라고 범위를 밝힌다.
- (b) 4.4절 l.52 뒤에 "선택 문맥은 전체 생성 입력의 약 9%로, 근거 수 조정에 따른 생성 입력 변화의 상한이 작다"는 취지의 문장을 추가한다.

### W3: 선택 후 필터링의 동기와 자원 효과가 연결되지 않았다 (P2)
- **Severity**: Minor
- **Evidence Anchor**: text: §4.4 l.69 "필터링은 유지 근거 수를 줄였을 뿐이며, 이에 따른 비용·지연 변화는 측정하지 않았다"
- **Confidence**: 4 — 운영 관점의 실험 설계 판단.

**문제.** 4.4절 l.54는 필터링을 "추가로 … 수행하였다"로만 시작하고 목적을 밝히지 않는다. 배포 독자는 필터링을 문맥·비용 절감 수단으로 읽게 되는데, 바로 그 효과는 "측정하지 않았다"로 끝난다. 그 결과 4.4절에서 가장 큰 분량을 차지하는 분석의 실무 가치가 불분명해진다.

**기존 자료로 가능한 보완.** 새 생성 없이 할 수 있다.
- `e2e-summary.json`에 필터링 후 문맥 길이(문자 수 평균 CE 302.6, Jev 282.8)와 근거 수(Jev 문항당 1.88개)가 이미 있다.
- S3과 같은 `o200k_base` 방식으로 필터링 후 문맥 토큰을 오프라인 계산할 수 있다.
- Jev+필터링에서 재생성된 45문항은 trace에 실제 사용량이 남아 있다.

**제안.**
- l.54 첫 문장에 필터링의 목적(예: 생성 문맥 축소 가능성 탐색)을 한 구절로 밝힌다.
- l.69에 "문맥 토큰은 평균 약 X토큰(전체 입력의 Y%) 감소"를 보고한다. "비용·지연 미측정"은 "청구액·지연 미측정, 토큰 요구량은 Z"로 바꾼다.

### W4: Jev 비결정성의 운영 함의가 평균 하나로 요약되고, RQ1 결과와 떨어져 있다 (P1)
- **Severity**: Major
- **Evidence Anchor**: text: §4.3 l.46 "Jev의 순서 무관 후보 겹침은 목록별 교집합 비율을 문항 내 평균한 뒤 전체 실행에서 평균했을 때 91.51%였다"
- **Confidence**: 4 — 외부 API 모델의 회귀 테스트·감사 운영 경험. 분포 수치는 심사자가 `raw.jsonl`에서 계산했으며 저자 확인이 필요하다.

**문제 1: RQ1 결과와의 거리.** RQ1의 F1 +3.19점은 비결정적 원격 서비스에서 한 번 실행한 결과다. 그런데 이 사실은 4.2절이 아니라 4.3절 마지막 문단에서야 나온다. 4.2절만 읽고 "교체 시 F1 +3점"을 기대하는 배포 독자가 생길 수 있다.

**문제 2: 꼬리 분포의 은폐.** 평균 91.51%는 꼬리를 가린다. 심사자가 `results/koblex-latency-v1/raw.jsonl`의 본 측정 180회를 계산해 보니 다음과 같았다.
- 문항–반복 단위 겹침의 최솟값은 0.60이다. 즉 한 문항에서 top-10의 40%가 바뀌었다.
- 하위 10%는 0.85 이하다.

운영에서 문제가 되는 것은 평균이 아니라 이런 꼬리 사례다. 어떤 문항에서 gold가 shortlist 안팎을 오가는 것이 바로 꼬리 사례에서 일어나기 때문이다.

**문제 3: 버전 고정의 범위.** 이름이 `jev-1.14.0`으로 고정되어 있어도, 같은 이름 아래 서버 측 가중치나 추론 경로가 바뀌지 않는다는 보장이 있는지는 장 안에서 알 수 없다. 측정 시점(품질 실행과 지연 실행의 날짜 차이)도 본문에 없다. 따라서 관측된 불일치가 호출 간 비결정성인지, 시점 간 서비스 변화인지 구분되지 않는다.

**제안.**
- (a) 4.2절 첫 문단 또는 그림 1 캡션에 "Jev 수치는 비결정적 원격 API의 단일 실행 결과(4.3절 참조)"라는 한 구절을 넣는다.
- (b) l.46에 겹침 분포의 하위 꼬리(최솟값, 하위 10% 값)를 덧붙인다.
- (c) 보충자료 S9에 품질 실행과 지연 실행의 날짜를 밝히고, 위 두 원인을 이 자료로는 구분할 수 없다고 명시한다.
- (d) 실무 함의로 한 문장을 둔다. 예: "재현 가능한 감사를 위해서는 재정렬 점수의 저장·재사용이 필요하다." 이는 저장 결과를 쓴 이 장의 실험 방식 자체와도 일관된다.
- 이 지적은 R1(단일 draw의 통계적 함의), R2(도메인 재현성)와 같은 사실에서 출발하지만, 관점은 다르다(운영 감사성).

### W5: 배포 조건 명세가 본문에서 부족하고, 이식성 높은 단위(쌍당 지연)가 빠졌다 (P2)
- **Severity**: Minor
- **Evidence Anchor**: text: §4.3 l.34 "CE는 로컬 MPS에서 float32·배치 50으로, Jev는 원격 API에서 동시 요청 4개로 실행하였다"
- **Confidence**: 4 — 추론 서빙 벤치마크 경험.

**문제.**
- 본문의 "로컬 MPS"는 하드웨어를 특정하지 못한다(README에는 Apple M5 Pro로 기록됨).
- 문항당 지연은 문항별 후보 쌍 수(83–287, 평균 177)에 비례하므로 다른 파이프라인으로 이식하기 어렵다. `summary.json`의 쌍당 지연을 보면 CE는 27.6ms, Jev는 60.2ms다. 특히 Jev의 쌍당 지연은 IQR이 59.2–60.9ms로 매우 안정적이어서, 후보 수에 대해 거의 선형으로 늘어나는 것으로 보인다. 이 수치는 "BM25 후보 수를 줄이면 Jev 지연이 비례해 준다"는 설계 판단에 바로 쓰인다.
- 일반화 방향도 서술할 가치가 있다. 서버 GPU에서 CE를 돌리면 CE가 빨라져 비율이 커질 것이다. Jev의 동시 요청 수를 늘리면 비율이 작아질 수 있다(속도 제한의 영향을 받음). 즉 2.25배는 두 손잡이(하드웨어, 동시성)에 따라 양방향으로 움직인다. 지금의 "일반화할 수 없다"보다 이 서술이 독자에게 더 유용하다.

**제안.** 표 1에 "후보 쌍당 평균(ms)" 행을 추가한다(기존 자료). l.34에 하드웨어명을 적는다. 동시성 4를 고른 이유(예: 기본값, 속도 제한)를 한 구절로 밝힌다.

### W6: 표 1의 "제95백분위수"가 SLO 독자에게 요청 단위 꼬리로 오독될 수 있다 (P2)
- **Severity**: Minor
- **Evidence Anchor**: table: 표 1 (§4.3 l.36–42, "제95백분위수" 행)
- **Confidence**: 5 — latency SLO 보고 관례.

**문제.** p95는 문항별 3회 평균 60개의 분포에서 계산한 값이다. 캡션에 그렇게 적혀 있지만, SLO 맥락의 독자는 p95를 습관적으로 요청 단위 꼬리로 읽는다. 또한 반복 간 변동계수는 CE 16.93%, Jev 3.43%로 S9에만 있다. 이는 "CE가 평균은 빠르지만 덜 예측 가능하다"는 운영상 유의미한 대비인데 본문에서 빠졌다.

**제안.**
- 표 행 이름을 "문항 평균의 제95백분위수"로 바꾼다.
- 표 아래 또는 l.44에 변동계수 대비를 한 구절로 넣는다. 다만 CE 변동의 원인(MPS 열 관리 등)은 단정하지 않는다.

### W7: Jev 비용 0.61달러가 정규화되지 않아 해석할 수 없다 (P2)
- **Severity**: Minor
- **Evidence Anchor**: text: §4.4 l.69 "지연 벤치마크의 Jev 본 측정 요청 비용은 약 0.61달러였으나"
- **Confidence**: 4 — 비용 회계 관례. 단위 비용은 심사자가 `raw.jsonl`에서 계산했다.

**문제.** 총액 0.61달러는 반복 횟수와 표본 크기에 종속된 값이라 독자가 쓸 수 없다. 심사자 계산으로는 본 측정 180회 기준 **문항당 약 $0.0034**, **후보 1,000쌍당 약 $0.019**다. trace 기준으로 같은 문항의 GPT-4o 호출 비용(선택 호출당 약 $0.012, 답변 생성 약 $0.005)과 나란히 놓으면, Jev 재정렬의 API 비용은 LLM 호출 비용 대비 작은 편(대략 한 자릿수 %에서 10% 안팎)으로 보인다. 이것은 "지연은 크게 늘지만 API 비용 증가는 상대적으로 작다"는, 배포 판단에 쓸 수 있는 메시지다. 단, 로컬 CE의 장비·전력비가 빠져 있다는 기존 유보는 그대로 유지해야 한다.

**제안.** l.69의 총액을 문항당·쌍당 단가로 바꾸거나 함께 적는다. 같은 단위의 LLM 단계 비용을 참고치로 나란히 적되, "청구 기록 기반 참고치이며 총비용 비교가 아님"이라는 범위 한정을 유지한다.

### W8: 원격 재정렬기로 법률 질의를 외부 전송하는 데 따른 거버넌스 차이가 배포 조건 서술에서 빠졌다 (P2)
- **Severity**: Minor
- **Evidence Anchor**: absence: §4.3 l.34·l.44 및 §4.4 l.69의 배포 조건 서술 — expected 로컬 CE와 원격 Jev 사이의 데이터 외부 전송·가용성 차이에 대한 한 구절; checked 본문 4.1–4.5, 보충자료 S3·S9, `results/koblex-latency-v1/README.md`
- **Confidence**: 3 — 법률 서비스 배포 거버넌스 일반론. 해당 서비스의 데이터 처리 조건은 확인하지 않았다.

**문제.** 장은 "로컬 CE vs 원격 Jev"를 지연 차이의 맥락으로만 다룬다. 실무에서 이 구분은 질의와 후보 법령 텍스트(실서비스라면 사용자 사건 정보 포함)가 제3자 엔드포인트로 나가는지, 그 서비스의 가용성에 의존하는지의 차이이기도 하다. KoBLEX는 공개 데이터이므로 이 실험 자체에는 문제가 없다. 하지만 결과 장이 배포 조건을 언급하는 이상 한 구절은 필요하다. 이번 측정에서 실패·재시도가 0건이었다는 점은 가용성에 대한 긍정적 관측이므로 이미 보고한 것이 좋다. 다만 단일 세션 360회라는 범위를 함께 적어야 한다.

**제안.** l.44의 배포 조건 문장에 "데이터 외부 전송 여부와 외부 서비스 가용성도 두 배포 조건의 차이"라는 구절을 추가한다. 상세 논의는 다른 장으로 넘긴다(팀 조율 메모 2).

### W9: 점수 척도의 운영 활용성(문턱값 설정 가능성)과 선택 전 필터링의 실무 함의가 해석되지 않았다 (P2)
- **Severity**: Minor
- **Evidence Anchor**: text: §4.4 l.65 "선택 전 필터링에서는 shortlist 후보를 약 절반으로 줄일 때 문항별 gold 출현 443건 기준 유지 비율이 CE 66.14→51.47%, Jev 72.69→69.30%였다"
- **Confidence**: 3 — 운영 관점 해석. 선택 전 필터링이 최종 결과에 주는 영향은 측정되지 않았다.

**문제.** 배포자에게는 두 가지 사실이 중요하지만 본문은 해석 없이 넘어간다.
1. **문턱값 설정 가능성.** CE의 fold별 문턱값은 약 3.7×10⁻⁶이고 Jev는 0.30–0.40이다(S7). README를 보면 CE 점수는 대부분 0.05 미만이어서 절대 격자로는 필터링이 사실상 불가능했다. 즉 Jev 점수는 기권(abstention)이나 문턱값 운용에 바로 쓸 수 있는 척도이고, CE 점수는 분위수 변환 없이는 쓰기 어렵다. 이것은 품질과 별개인 배포 속성이다.
2. **선택 전 필터링의 레버.** shortlist를 절반으로 줄여도 Jev는 gold 유지율이 거의 떨어지지 않는다. W2에서 보았듯 선택 호출은 토큰을 가장 많이 쓰는 단계로 보이므로, 이 결과는 선택 단계 입력을 줄이는 레버가 될 수 있다. 그러나 LLM 선택을 다시 실행하지 않았으므로 최종 효과는 알 수 없다.

**제안.** l.65 뒤에 한 문장을 둔다. 예: "shortlist 축소는 선택 호출 입력을 줄일 수 있는 방향이나, 재선택을 수행하지 않아 최종 효과는 확인되지 않았다." 문턱값 척도 차이는 l.54의 분위수 격자 설명에 "CE 점수가 0 근처에 몰려 절대 격자로는 필터링이 어려웠다"는 사실로 한 구절 보강한다. 재선택 실험은 선택적 후속 연구로 둔다.

### 상세 의견 (Detailed Comments)

**가정 점검(Assumption Audit).**
- 명시적 가정: 재정렬 단계만 떼어 비교해도 의미가 있다(장은 이 가정을 한정적으로 다룸).
- 암묵적 가정: (i) 생성 단계 토큰이 자원 사용을 대표한다(W2). (ii) 저장된 단일 Jev 실행이 서비스의 대표 동작이다(W4). (iii) 동시성 4는 중립적인 설정이다(W5).
- 패러다임 가정: 품질은 오프라인 지표로, 비용·지연은 별도 실행으로 본다. 오프라인 평가 관례로서 정당하다. 다만 품질과 시간을 같은 실행에서 재지 않았다는 사실은 장이 이미 명시했다.

**인접 분야 연결.** 이 장이 보고한 운영 사실들은 ML systems 문헌의 오래된 주제와 이어진다. 원격 API 의존 모델의 시간 변화·비결정성, 외부 의존성이라는 기술 부채, 다단계 서비스의 tail latency 증폭이 그것이다. 짧은 결과 장에 문헌을 넣을 필요는 없지만, 논의 장에서 위치를 잡을 때 쓸 수 있다(아래 참고문헌 제안, UNVERIFIED).

**실무 영향.** 이 장의 결과를 실무 문장으로 옮기면 대략 다음과 같다(W1·W2·W7 보완이 전제).
- 근거 F1을 약 3점 얻는 대가로 재정렬 지연이 약 5–6초 늘어난다. 이 증가는 LLM 단계 전체와 비슷하거나 더 클 수 있다.
- API 비용 증가는 상대적으로 작다.
- 감사를 위해서는 점수를 저장해야 한다.

이 정도로 정리되면 배포 독자에게 매우 유용하다. 현재는 이 문장을 독자가 보충자료와 원자료에서 직접 재구성해야 한다.

**더 넓은 함의.** 법률처럼 민감한 질의를 다루는 영역에서는 로컬 모델과 원격 API 사이의 선택이 품질·지연만의 문제가 아니다(W8). 결과 장에는 한 구절이면 충분하다.

### 팀 조율 메모 (cross-chapter; 제4장 수정 요구 아님)
1. **방법 장.** Jev/Decision Model이 원격 API로만 제공되는지, 온프레미스 배포가 가능한지, 버전 고정 정책이 무엇인지를 서술하면 4.3절의 "배포 조건 의존" 문장이 독자에게 구체적으로 읽힌다.
2. **논의·한계 장.** 법률 질의의 외부 전송(데이터 거버넌스), 외부 서비스 가용성, 비결정성에 따른 감사 가능성을 배포 고려사항으로 다룰 것을 권한다(W4, W8의 상세판).
3. **서론·초록·결론.** 다른 장에서 Decision Model을 "효율적" 또는 "비용·입력량 절감"으로 기대하게 만드는 문장이 있다면, 제4장 결과와 맞춰야 한다. 제4장 결과는 토큰 소폭 증가, 재정렬 지연 약 2.25배, 필터링 자원 효과 미측정이다.
4. **결론 장.** 지연 수치를 인용할 때 "재정렬 단계" 한정어를 빠뜨리지 않도록 한다(E2E로 오독 방지).
5. **용어 통일.** "지연", "응답시간", "실행 시간"을 장 전체에서 같은 뜻으로 쓰고, 영문 번역 시에는 각각 reranking latency, end-to-end latency, wall-clock time으로 구분한다.
